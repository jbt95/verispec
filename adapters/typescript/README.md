# VeriSpec adapter for TypeScript and JavaScript

This package holds the **trace recorder** for TypeScript and JavaScript: the
piece that records what your implementation did, so that
`verispec check-trace` can decide whether it follows the contract.

It ships two builds: ESM (`import`) and CommonJS (`require`), so a plain
JavaScript project can use it either way.

The property tests are generated by the VeriSpec CLI, not shipped here. A
generated test is derived from your spec, so it never goes stale. The CLI has
one generator per dialect:

```console
$ verispec gen-tests specs/bank.yaml --lang typescript  -o tests/bank.verispec.gen.ts
$ verispec gen-tests specs/bank.yaml --lang javascript -o tests/bank.verispec.gen.js
```

The two files are the same test: the same expressions, transpiled from the
same AST, the same runtime helpers, the same `runConformance(makeAdapter)`
entry point. The JavaScript one has no type syntax, and the types travel as
JSDoc.

## Install

```bash
npm install --save-dev @verispec/adapter fast-check
```

```javascript
// ESM
import { TraceRecorder } from '@verispec/adapter';

// CommonJS
const { TraceRecorder } = require('@verispec/adapter');
```

## The trace recorder

```typescript
import { TraceRecorder } from "@verispec/adapter";
import { makeAdapter } from "./my-adapter";

const recorder = new TraceRecorder(makeAdapter());
recorder.reset();
recorder.apply("transfer_a_to_b", { amount: 20 });
recorder.write("traces/session.json");
```

Then:

```console
$ verispec check-trace specs/bank.yaml traces/session.json
trace OK: 2 steps conform to spec Bank
```

The trace is the canonical JSON format: a list of
`{action, params, state}`, the first entry with `action: "init"`. Maps are
objects with stringified keys, sets and sequences are arrays, records are
objects keyed by field name.

The guarantee of that result is `conformance-tested`: a recorded run of the
real implementation was replayed against the spec and every step conformed.
It says nothing about the runs that were not recorded.

## The generated property test

```console
$ verispec gen-tests specs/bank.yaml --lang typescript -o tests/bank.verispec.gen.ts
```

The generated module exports `runConformance(makeAdapter)`. Wire it to your
runner in two lines:

```typescript
import { test } from "vitest";
import { runConformance } from "./bank.verispec.gen";
import { makeAdapter } from "./my-adapter";

test("verispec conformance", () => {
  runConformance(makeAdapter);
});
```

The generated file is self-contained: the spec expressions are transpiled
from the same AST the Z3 checker uses, and the runtime helpers are emitted
inline. It needs `fast-check` and nothing else.

## The adapter contract

Three methods, and the state is exactly the spec's variables:

| Method | Meaning |
| --- | --- |
| `reset()` | Put the implementation in the spec's initial state. |
| `apply(action, params)` | Apply one action of the spec. |
| `snapshot()` | The current state, with exactly the spec's variables. |

The adapter should call your real code, not reimplement it, and it must not
clamp or repair values: an adapter that "fixes" the state hides the defect
the conformance test is looking for.

## The conformance suite

```console
$ npm test
```

The suite checks the four things every adapter has to pass:

1. the generated property test passes on the correct adapter,
2. it **fails** on the deliberately broken adapter,
3. the trace recorder writes the canonical format,
4. `verispec check-trace` accepts the recorded trace.

It runs twice: once against the TypeScript conformance test, once against the
JavaScript one, plus a check that the CommonJS build works.

The `pretest` step regenerates both conformance tests with the VeriSpec CLI,
so the suite always runs against the current spec. It needs the CLI on the
`PATH` (`pip install verispec`).
