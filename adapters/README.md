# VeriSpec adapters

An adapter is the small, language-specific piece that connects a real
implementation to a VeriSpec spec. It is deliberately tiny: three methods and
a state.

| Directory | Language | What is in it |
| --- | --- | --- |
| [`rust/`](rust/) | Rust | The `verispec-adapter` crate: the runtime, the trace recorder and the conformance suite. |
| [`c/`](c/) | C | The `verispec.h` runtime, the trace recorder and the conformance suite. Scalar specs only. |
| [`typescript/`](typescript/) | TypeScript and JavaScript | The trace recorder package, with ESM and CommonJS builds. The property tests are generated by the CLI (`--lang typescript` and `--lang javascript`). |
| [`java/`](java/) | Java | The trace recorder package. The property tests are generated by the CLI. |
| [`conformance/`](conformance/) | - | The shared conformance spec every adapter is checked against. |

The full authoring guide is in
[`docs/adapter-authoring.md`](../docs/adapter-authoring.md); the per-language
recipes are in
[`docs/language-integrations.md`](../docs/language-integrations.md).

## The contract

| Concept | Python | TypeScript | JavaScript | Go | Rust | C |
| --- | --- | --- | --- | --- | --- |
| Reset | `reset()` | `reset()` | `reset()` | `Reset()` | `reset(&mut self)` | `veri_reset(void)` |
| Apply | `apply(action, **params)` | `apply(action, params)` | `apply(action, params)` | `Apply(action, params)` | `apply(&mut self, action, params)` | `veri_apply(action, params_json)` |
| Snapshot | `snapshot() -> dict` | `snapshot() -> Record<string, any>` | `snapshot()` | `Snapshot() map[string]any` | `snapshot(&self) -> Value` | `veri_snapshot(out, len)` |

The rules that do not change:

- The action names and the parameter names are the ones in the spec, exactly.
- `snapshot()` returns **every** variable of the spec and nothing else. A
  missing variable is an error; an extra variable is a state the spec does
  not describe.
- A map is a JSON object with stringified keys (`"0"` for the integer key
  `0`), a set and a sequence are JSON arrays, a record is a JSON object
  keyed by field name, and an enum value is a string.
- The adapter reports the truth. It does not clamp, round or repair a value:
  an adapter that hides a defect makes the conformance test worthless.

## Writing an adapter

An adapter is a translation layer, not a place for logic:

1. It calls the real implementation; it does not reimplement the business
   rule. An adapter that reimplements the rule proves that the adapter is
   correct, which is not the point.
2. It is small enough to review. If the adapter is longer than the code it
   wraps, the spec probably describes the wrong thing.
3. It enforces the preconditions and throws when they do not hold. The
   generated test only calls enabled actions, so a broken implementation
   would otherwise never be noticed.

```rust
// Rust
use serde_json::Value;
use std::collections::HashMap;
use verispec_adapter::VeriSpecAdapter;

pub struct BankAdapter {
    balance_a: i64,
    balance_b: i64,
}

impl BankAdapter {
    pub fn new() -> Self {
        BankAdapter { balance_a: 50, balance_b: 50 }
    }
}

impl VeriSpecAdapter for BankAdapter {
    fn reset(&mut self) {
        self.balance_a = 50;
        self.balance_b = 50;
    }

    fn apply(&mut self, action: &str, params: &HashMap<String, Value>) {
        let amount = params.get("amount").and_then(|v| v.as_i64()).unwrap_or(0);
        match action {
            "transfer_a_to_b" => {
                assert!(amount > 0 && self.balance_a >= amount, "precondition");
                self.balance_a -= amount;
                self.balance_b += amount;
            }
            other => panic!("unknown action {other}"),
        }
    }

    fn snapshot(&self) -> Value {
        serde_json::json!({ "balance_a": self.balance_a, "balance_b": self.balance_b })
    }
}
```

## Generating the conformance test

```console
$ verispec gen-tests adapters/conformance/bank.verispec.yaml --lang rust \
    --adapter my_crate::BankAdapter -o tests/verispec_conformance.rs
$ cargo test --test verispec_conformance
```

```console
$ verispec gen-tests adapters/conformance/bank.verispec.yaml --lang c \
    -o conformance/verispec_conformance.c
$ cc -Iadapters/c/include -o conformance/verispec_conformance \
    conformance/verispec_conformance.c my_adapter.c adapters/c/src/verispec.c
$ ./conformance/verispec_conformance
```

The generated test drives the adapter with random (but reproducible) action
sequences and checks three things at every step:

1. after `reset()`, the state equals the state the spec's `init` block
   prescribes;
2. after an action, the state equals what the spec's `effects` prescribe;
3. every state, including the initial one, satisfies every invariant.

Actions whose preconditions do not hold are skipped, not applied.

## The conformance suite

Every adapter ships the same suite, and the third part is the one people
forget:

| # | Check | Expected result |
| --- | --- | --- |
| 1 | The generated test, correct adapter | Pass. |
| 2 | A recorded trace, `verispec check-trace` | `trace OK`. |
| 3 | The generated test, deliberately broken adapter | **Fail.** |
| 4 | `verispec corpus corpus` | No failures. |

The broken adapter must break the contract in a way the spec actually
constrains: it leaks one unit on every transfer, so the total is not
conserved. A suite that stays green on it is not testing anything.

## What an adapter never claims

The generated tests and the recorded traces are **conformance-tested**
evidence. They show that the implementation agrees with the spec on the
states the run reaches. They are not a proof, and no adapter output may be
described as one.

The guarantee labels are defined in
[`docs/guarantees.md`](../docs/guarantees.md).
